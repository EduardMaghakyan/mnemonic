# Phase 0 — v0.3 image attachment spike findings

**Date:** 2026-05-10
**Verdict:** PASS — single-request dual-modality works. Proceed to implementation with audio + image in one `/v1/chat/completions` call. No two-pass fallback needed.

## What was tested

Whether `llama-server` running Gemma 4 E4B (Q4_K_M + audio-capable mmproj) accepts an `input_audio` content part **and** an `image_url` content part in the same `/v1/chat/completions` request, and whether the model returns coherent JSON covering both modalities.

Artifacts:
- WAV: `audio/sample.wav` (the existing Phase 0 sample, ~13s of speech)
- Images: `images/test-stacktrace.png` (terminal panic, 24 KB), `images/test-mockup.png` (UI mockup, 1.6 KB), generated by `images/make-test-image.py`
- Runner: `run-image-spike.sh`
- Responses: `responses/stacktrace-response-*.json`, `responses/mockup-response-*.json`

## Setup

Same as the v0.1 spike — `unsloth/gemma-4-E4B-it-GGUF:Q4_K_M`, mmproj-BF16, server flags `--mmproj-auto -ngl 99 -c 8192`. No server changes needed; the vision encoder is already present in the same mmproj that handles audio.

## Request shape that worked

Three content parts in the user message: `input_audio` + `image_url` (data URL with base64 PNG) + a short `text` instruction. Server accepts the combination without any flag tweaking.

```json
"messages": [
  { "role": "system", "content": "<schema + rules>" },
  { "role": "user", "content": [
    { "type": "input_audio", "input_audio": { "data": "<base64 WAV>", "format": "wav" } },
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,<base64 PNG>" } },
    { "type": "text", "text": "Process this voice memo. An image is attached. Return only the JSON object." }
  ]}
]
```

## Schema that the model followed cleanly

```json
{
  "cleaned": "string — the user's spoken note, voice rules same as v0.2",
  "image_note": null
                | { "kind": "text",    "text": "verbatim text from the image" }
                | { "kind": "caption", "caption": "one-line description, no extractable text" }
}
```

The model picked `kind: "text"` for the stack trace (and reproduced the panic message and source-line pointer verbatim) and `kind: "caption"` for the UI mockup ("A screenshot of a user interface with input fields and a button."). It honored the "never both" rule both times. Audio transcription continued to obey the v0.2 voice rules in `cleaned`.

## Performance

| Image | Prompt tokens | Completion tokens | Wall-clock |
|---|---|---|---|
| stack-trace PNG (24 KB) | 976 | 804 | **36 s** (cold cache) |
| UI mockup PNG (1.6 KB) | 945 | 543 | **17 s** (668 tokens cached from prior request) |

So the cold-start hit is ~30s for the first dual-modal call in a session; subsequent calls reuse the system-prompt cache and run in the same range as v0.2 voice-only (~15–20 s).

## Decisions for implementation

1. **Single request, no two-pass fallback in the primary path.** Two-pass code can stay out of the codebase entirely until/unless we hit a real failure mode.
2. **Schema lives in `core/src/schema.rs`** as `StructuredNote { cleaned, image_note: Option<ImageNote> }` with `ImageNote::{Text, Caption}`. Backward-compatible — existing voice-only flow returns `image_note: None`.
3. **System prompt stays one file** (`core/src/system_prompt.txt`) with a new "Image rules" block + the two calibration examples observed here.
4. **PNG transport.** Encode RGBA8 from the clipboard into PNG bytes on the app side, base64 + data URL on the wire. Cap at ~4 MB pre-base64 to stay polite to the server.
5. **No new tray hotkey.** Existing voice hotkey reads the clipboard at recording-start; if an image is present, attach it. Notification ("Recording with screenshot") confirms.
